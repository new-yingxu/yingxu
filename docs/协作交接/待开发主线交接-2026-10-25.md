## 4. RAW 格式分析

### 现状

- `backend/core/src/media.rs` 已有：`index_source`、`analyze_photo`、`thumbnail`、`review_media`、`duplicate_candidates`
- 依赖：`image 0.25.10`（jpeg/png/tiff/webp/bmp）+ `kamadak-exif 0.6`
- **RAW 完全不支持**（`.cr2/.cr3/.nef/.arw/.raf/.dng/.orf/.rw2` 等）

### 任务

1. **选型**（先验证再定）：
   | 方案 | 优点 | 代价 |
   |---|---|---|
   | LibRaw（`libraw-sys` 绑定） | 覆盖最广、工业级 | LGPL-2.1/CDDL 双许可、需编译 C、包体积 +5~10MB |
   | `rawloader`（纯 Rust） | 无 C 依赖、许可简单 | 机型覆盖有限、维护活跃度需核 |
   | `rawler`（纯 Rust） | 支持部分新机型 | 生态较新，稳定性待验 |
2. **优先走"内嵌预览"**：多数 RAW 内含 JPEG 预览图，提取预览做缩略图比完整解码快一个数量级。
3. **EXIF 提取**：相机型号、镜头、拍摄时间、ISO、光圈、快门、方向；时间优先用 EXIF，缺失回退文件时间并标注来源。
4. **缩略图**：沿用现有 512px 无 EXIF JPEG 策略。
5. **样本矩阵**：按目标品牌（佳能/尼康/索尼/富士/松下）各取 3~5 个真实样本，记录成功率、耗时、内存峰值。
6. **许可合规**：若用 LibRaw，写清动态链接方式与许可证声明，随安装包分发。
7. **不承诺**：LibRaw 官方说明其基础转换不以生产级渲染为目标 —— 我们只做**读取与预览**，不做高质量显影。

### 验收

- [ ] 样本矩阵内每个机型都能提取预览 + EXIF
- [ ] 不支持的格式明确提示"暂不支持"，而不是静默失败
- [ ] 单文件内存峰值有上限，超大文件不 OOM
- [ ] 原片只读，哈希不变

## 5. 视频分析

### 现状

零。`index_source` 可能仅按扩展名归类为 `video`，无任何解码/分析。

### 任务

1. **元数据**：时长、分辨率、帧率、编码、码率、创建时间。方案二选一：
   - 外挂 `ffprobe`（需随包分发二进制，体积 +30~80MB，许可 LGPL）
   - 纯 Rust（`mp4parse` / `symphonia`，覆盖 MP4/MOV，不覆盖全部容器）
2. **抽帧**：从 10%/50%/90% 位置各取 1 帧（关键帧优先），用于模糊/曝光判断。
3. **质量候选**：复用照片的曝光/清晰度逻辑，输出"待复核"而非自动判定。
4. **资源控制**：大文件流式读取，禁止整文件入内存；单文件解码有时间与内存上限，超限记 `resource_limit` 而非崩溃。
5. **隐私边界**：视频默认**只在本机分析**，不抽帧上传；云端视觉能力若启用，须用户逐条选择并确认。

### 验收

- [ ] 常见手机/相机视频（MP4/MOV）能读出元数据并抽帧
- [ ] 4K 长视频不 OOM、不卡死
- [ ] 不支持的容器明确提示
- [ ] 无任何帧数据离开本机
